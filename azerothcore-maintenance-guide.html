Démarrer / arrêter le serveur

Toujours commencer dans le dossier du projet.

cd C:\azerothcore-playerbots

Démarrer tout le serveur

docker compose up -d
Le -d lance les conteneurs en arrière-plan.

Arrêter proprement les services

docker compose stop

Relancer après un arrêt

docker compose start
À éviter : docker compose down -v. Le -v supprime les volumes, donc potentiellement les bases, comptes et personnages.

Vérifier l'état

docker compose ps

État attendu :

ServiceÉtat souhaité
ac-databaseUp / healthy
ac-authserverUp
ac-worldserverUp

Ressources utilisées

docker stats --no-stream

Voir les conteneurs Docker actifs

docker ps

Logs

Suivre le worldserver en direct

docker compose logs -f ac-worldserver

Quitter l'affichage des logs avec Ctrl+C. Cela ne coupe pas le serveur.

Dernières lignes seulement

docker compose logs --tail=100 ac-worldserver

Chercher un module ou une erreur

docker compose logs --tail=300 ac-worldserver | Select-String -Pattern "MountChest|ERROR|Missing property"

Console du worldserver

Dans notre configuration, docker attach ac-worldserver a parfois renvoyé immédiatement read escape sequence. La variante avec une touche de détachement explicite est préférable. 
docker attach --detach-keys="ctrl-x" ac-worldserver

Une fois attaché, utiliser les commandes AzerothCore, par exemple :

account create test test
account set gmlevel test 3 -1

Pour quitter la console sans éteindre le serveur : Ctrl+X.

Ne jamais lancer manuellement un second worldserver depuis un shell du conteneur.

Redémarrage ciblé

Redémarrer uniquement le worldserver

docker compose restart ac-worldserver

Après modification des variables d'environnement

Un simple restart ne recrée pas le conteneur. Utiliser :

docker compose up -d --force-recreate ac-worldserver

Redémarrer world + auth

docker compose up -d --force-recreate ac-worldserver ac-authserver

Configuration Docker / modules

Notre fichier principal de personnalisation est généralement :

C:\azerothcore-playerbots\docker-compose.override.yml

Valider le YAML avant de lancer

docker compose config

Exemple actuel du bloc worldserver

services:
  ac-worldserver:
    environment:
      AC_AI_PLAYERBOT_RANDOM_BOT_AUTOLOGIN: "1"
      AC_AI_PLAYERBOT_MIN_RANDOM_BOTS: "200"
      AC_AI_PLAYERBOT_MAX_RANDOM_BOTS: "500"

      AC_MOUNT_CHEST_ENABLE: "1"
      AC_MOUNT_CHEST_OWNER_ONLY: "1"
      AC_MOUNT_CHEST_LIFETIME_SECONDS: "120"
      AC_MOUNT_CHEST_MONEY_MIN: "10"
      AC_MOUNT_CHEST_MONEY_MAX: "50"

    volumes:
      - ./modules:/azerothcore/modules:ro
Si les logs disent Missing property X, vérifier le fichier de config du module ou ajouter la variable d'environnement correspondante, puis recréer le worldserver.

SQL / patches de modules

Appliquer le SQL de notre module de coffre

Get-Content .\modules\mod-mount-chest\sql\install.sql | docker exec -i ac-database mysql -uroot -ppassword acore_world

Tester une requête

docker exec ac-database mysql -uroot -ppassword acore_world -e "SELECT entry,name FROM gameobject_template WHERE entry IN (900001,900002,900003);"
L'avertissement Using a password on the command line interface can be insecure est attendu avec cette méthode locale.
Ne jamais supprimer/recréer le volume MySQL pour corriger un simple problème de module.

Sauvegarder la base

Avant une grosse mise à jour, faire au minimum un dump des trois bases principales.

mkdir C:\azerothcore-backups -ErrorAction SilentlyContinue

docker exec ac-database mysqldump -uroot -ppassword acore_auth > C:\azerothcore-backups\acore_auth.sql
docker exec ac-database mysqldump -uroot -ppassword acore_characters > C:\azerothcore-backups\acore_characters.sql
docker exec ac-database mysqldump -uroot -ppassword acore_world > C:\azerothcore-backups\acore_world.sql
Pour une sauvegarde importante, dater les fichiers et vérifier qu'ils ne font pas 0 octet.

Recompiler le worldserver

À faire après modification du C++ d'un module, ajout/suppression de module ou changement nécessitant une nouvelle image.

1. Libérer les ressources

docker stop ac-worldserver ac-authserver

2. Compiler

docker compose build ac-worldserver

3. Redémarrer avec la nouvelle image

docker compose up -d --force-recreate ac-worldserver ac-authserver

4. Contrôler

docker compose ps
docker compose logs --tail=150 ac-worldserver
Les Playerbots peuvent faire consommer beaucoup de CPU/RAM au worldserver. Pour une grosse recompilation, il est préférable de couper world/auth mais de laisser MySQL tranquille.

Installer / mettre à jour un module

Installation assistée depuis le catalogue

Dans Modules & dossiers → Installer depuis le catalogue, rechercher le module, ouvrir Catalogue pour consulter sa fiche officielle ou GitHub pour lire son README et ses prérequis, puis cliquer sur Installer et confirmer.

Le dashboard accepte uniquement les dépôts GitHub de la catégorie officielle azerothcore-module dont le nom commence par mod-. Il clone le dépôt dans modules, vérifie la présence d'un CMakeLists.txt à la racine et publie le dossier en une seule opération. Il n'exécute aucun script du module, n'applique aucun SQL et ne lance pas automatiquement le rebuild.
  1. Lire le README du module et vérifier sa compatibilité avec la version du core.
  2. Installer le module depuis le dashboard.
  3. Examiner les éventuelles étapes de configuration ou migrations SQL documentées par son auteur.
  4. Lancer Rebuild AzerothCore, puis contrôler les logs.
La présence dans le catalogue n'est pas un audit de sécurité. Ne lance pas un script ou un SQL tiers sans l'avoir examiné et sans sauvegarde adaptée. Le dashboard refuse aussi de remplacer un dossier de module existant.

Supprimer un module

Dans Modules & dossiers → État des modules, cliquer sur Supprimer…. Le dashboard présente séparément le dossier du module, ses configurations actives détectées et les éventuels scripts SQL de désinstallation. Choisir les éléments voulus, relire le récapitulatif, puis saisir exactement le nom du module pour confirmer. Les configurations actives sélectionnées sont sauvegardées avant suppression.

Le nettoyage SQL est désactivé par défaut et modifie réellement la base. Il n'est proposé que lorsqu'un script dont le nom indique explicitement une désinstallation (uninstall, remove, delete ou drop) se trouve sous le dossier SQL d'une base identifiable. Lire ce script et effectuer une sauvegarde DB avant de confirmer : le dashboard ne peut pas annuler son exécution. Si un script SQL échoue, le dossier du module est conservé. Après toute suppression de module, lancer un rebuild.
L'onglet Modules & dossiers du dashboard vérifie automatiquement l'état de chaque module. Cette vérification est en lecture seule : elle compare un clone Git indépendant à son propre dépôt distant, ou les modules copiés au dépôt custom groupé. Aucun fichier de module, aucune configuration et aucune base de données ne sont modifiés par ce contrôle.

Mise à jour assistée

Lorsqu'une différence est détectée et que la source distante est connue, cliquer sur Mettre à jour puis confirmer. Le dashboard télécharge la nouvelle version dans un dossier temporaire, vérifie son CMakeLists.txt, déplace la version locale complète dans module-backups, puis publie la nouvelle version. Une erreur avant le remplacement laisse le module intact ; une erreur pendant le remplacement restaure automatiquement la sauvegarde.

La sauvegarde contient aussi les modifications locales non commitées, mais celles-ci ne sont pas fusionnées dans la nouvelle version. Examiner le backup pour les reporter si nécessaire. La mise à jour n'exécute aucun SQL, ne change aucune configuration et ne lance aucun rebuild : lire les notes du module, appliquer manuellement les migrations nécessaires avec une sauvegarde adaptée, puis lancer Rebuild AzerothCore.
  1. Arrêter ac-worldserver et ac-authserver.
  2. Faire une copie du module en dehors du dossier modules.
  3. Remplacer les fichiers dans modules\nom-du-module.
  4. Appliquer son SQL si nécessaire.
  5. Recompiler le worldserver.
  6. Recréer world/auth.
  7. Contrôler les logs.

Sauvegarde correcte d'un module

Copy-Item .\modules\mod-mount-chest C:\mod-mount-chest-backup -Recurse
Ne mets pas un dossier comme mod-mount-chest-v1-backup dans .\modules. AzerothCore le considère comme un vrai module et peut générer une erreur de linker undefined reference to Add...Scripts().

Mettre à jour le dashboard

L'indicateur en haut à droite liste les branches publiées du dépôt officiel. La branche choisie est comparée à l'installation locale uniquement au moyen de son manifeste contrôlé dashboard-update-manifest.json.

  1. Choisir main ou une branche de test dans le menu déroulant.
  2. Cliquer sur Mettre à jour (ou Revenir à main).
  3. Valider la boîte de dialogue qui rappelle la branche et l'effet du retour à main.
  4. Cliquer une seconde fois sur Confirmer la mise à jour dans les huit secondes.
  5. Attendre le message de réussite, puis redémarrer le dashboard pour charger le nouveau backend.
Avant remplacement ou suppression, les fichiers actuels sont copiés dans dashboard-backups\AAAAmmjj-HHMMSS-microsecondes. Le manifeste distant et le nom de branche sont validés avant toute écriture. L'auto-update ne synchronise jamais automatiquement l'intégralité du dépôt, ni le dossier AzerothCore : seuls les fichiers déclarés sont remplacés ; les modules, configurations, volumes Docker et bases de données ne sont pas touchés.
Pour quitter une branche de test, sélectionner main (principale). Le retour remplace les fichiers gérés par leurs versions principales et supprime les fichiers qui avaient été ajoutés au manifeste de la branche de test mais n'existent plus dans celui de main. Ces fichiers supprimés restent récupérables dans la sauvegarde horodatée. Les fichiers non déclarés par les manifestes ne sont jamais supprimés.
Si le catalogue de modules affiche qu'une page HTML n'est pas du JSON, le navigateur utilise une interface plus récente que le backend Python encore en mémoire. Fermer la console du dashboard, relancer dashboard.bat, puis actualiser le catalogue. Un simple rechargement du navigateur ne redémarre pas le backend.

Mettre à jour le core

Pour notre fork Playerbots, éviter de faire un git pull à l'aveugle juste avant de jouer. Faire une sauvegarde DB et vérifier les modules locaux avant.

Procédure prudente

cd C:\azerothcore-playerbots
docker stop ac-worldserver ac-authserver
git status
git pull
git submodule update --init --recursive
docker compose build ac-worldserver
docker compose up -d --force-recreate ac-worldserver ac-authserver

Ensuite contrôler immédiatement :

docker compose ps
docker compose logs --tail=200 ac-worldserver
Si le fork Playerbots ou un module impose une branche/version spécifique, conserver cette branche. Ne pas mélanger arbitrairement un core master différent avec des modules non compatibles.

Problèmes fréquents

Build : rpc error ... EOF

Souvent Docker Desktop / BuildKit perd la connexion, sans erreur C++.

docker compose build ac-worldserver

Si cela recommence : redémarrer Docker Desktop, puis relancer le build.

Build bloqué vers 1840/1844

Le linker final peut être lourd. Vérifier que l'ancien worldserver ne monopolise pas les ressources.

docker stats --no-stream
docker stop ac-worldserver ac-authserver

undefined reference to Addmod_..._backupScripts()

Un dossier de sauvegarde a probablement été laissé dans .\modules.

Move-Item .\modules\mod-mount-chest-v1-backup C:\mod-mount-chest-v1-backup

Missing property MountChest...

La config du module n'est pas chargée. Vérifier les variables dans docker-compose.override.yml, puis :

docker compose config
docker compose up -d --force-recreate ac-worldserver

read escape sequence avec docker attach

docker attach --detach-keys="ctrl-x" ac-worldserver

Puis quitter avec Ctrl+X.

MySQL : port 3306 déjà utilisé

Notre installation utilise le port hôte 3307 pour éviter le MySQL/MariaDB Windows déjà présent.
