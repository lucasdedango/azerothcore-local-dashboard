Le dashboard est le point d’entrée

Lancer dashboard.bat, conserver sa console ouverte, puis utiliser http://127.0.0.1:8765/. Le serveur Python reste lié uniquement à l’ordinateur local.

Dashboard

État de Docker et des conteneurs, démarrage, arrêt, restart, recreate, rebuild, patchs et dernière sortie.

Configs

Fichiers hôte et configs actives du conteneur, en texte brut ou en formulaire clé = valeur.

Compose override

Recherche d’options AzerothCore et ajout contrôlé de variables AC_*, avec validation et rollback.

Logs

100 ou 300 lignes, rafraîchissement automatique toutes les cinq secondes et suivi live dans une vraie console.

Modules & dossiers

Catalogue, état, installation, mise à jour et suppression assistées, plus accès aux dossiers de sauvegarde.

Fonctions prévues

Cette page est une feuille de route. Une carte affichée ici n’est pas encore une fonction active.

Démarrage quotidien

  1. Démarrer Docker Desktop et attendre que son moteur soit prêt.
  2. Double-cliquer sur dashboard.bat.
  3. Dans État serveur, cliquer Actualiser, puis Démarrer.
  4. Contrôler ac-database, ac-authserver et ac-worldserver, puis lire les dernières lignes de logs.
Arrêter seulement le dashboard : Ctrl+C dans sa console. Cela n’arrête pas les conteneurs. Le bouton Arrêter exécute docker compose stop et conserve conteneurs et volumes.
Jamais docker compose down -v. Les volumes peuvent contenir les comptes, personnages et mondes. Aucun workflow normal de ce dashboard ne demande leur suppression.

Choisir la bonne action

Restart, recreate et rebuild ne sont pas interchangeables. Choisir l’opération minimale réduit les interruptions et le risque.

Le rebuild actuel, étape par étape

  1. Vérifie Docker et peut proposer de démarrer Docker Desktop.
  2. Sauvegarde toutes les configs actives du worldserver.
  3. Conserve les valeurs existantes et ajoute uniquement les clés nouvelles des .conf.dist.
  4. Détecte les SQL de modules gérés par l’updater et propose une sauvegarde des quatre bases.
  5. Propose séparément les scripts PowerShell trouvés dans les modules, désactivés par défaut.
  6. Construit et recrée uniquement le worldserver, restaure les configs et redémarre.
  7. Contrôle l’état, les messages de l’updater et les SHA1 SQL enregistrés.
Le helper ne supprime ni ne recrée les volumes. Si le build échoue, les volumes de base existants ne sont pas touchés.
Le bouton Rebuild simple n’applique pas les deux patchs dédiés. Utiliser explicitement Patch + Rebuild lorsqu’ils sont requis.

Éditeur de configurations

La liste réunit .env, les fichiers Compose, les configs de modules présentes sur l’hôte et les fichiers ACTIVE du conteneur worldserver. docker cp permet aussi de lire un conteneur arrêté.

Workflow recommandé

  1. Choisir la source exacte, puis cliquer Charger.
  2. Modifier le texte brut, ou utiliser la vue visuelle pour les lignes reconnues clé = valeur.
  3. Après une modification brute, cliquer Reparser pour resynchroniser la vue visuelle.
  4. Cliquer Sauver. L’ancien contenu est d’abord copié sous config-backups\dashboard-*.
  5. Pour une config active, utiliser Restart world et vérifier les logs.
Le backup protège le fichier précédent, pas la validité métier d’une valeur. Modifier une option à la fois et lire la première erreur de démarrage.

Compose override assisté

  1. Rechercher une option native dans Compose override. La source est worldserver.conf.dist.
  2. Lire sa description et saisir la valeur souhaitée.
  3. Cliquer Ajouter. Le nom AC_* est calculé par le dashboard.
  4. L’ancien override est sauvegardé, puis docker compose config est exécuté.
  5. Si la validation échoue, le contenu précédent est restauré exactement et l’erreur reste visible.
  6. Si elle réussit, cliquer Recreate world.
Ne jamais contourner une erreur YAML. La restauration automatique est précisément là pour empêcher qu’un override invalide reste en place.

Installer, mettre à jour et supprimer un module

Vérification et catalogue

Revérifier est en lecture seule. Un clone Git indépendant est comparé à son dépôt propre ; les autres modules connus sont comparés au dépôt custom groupé. Le catalogue conserve seulement les dépôts GitHub de catégorie azerothcore-module, au nom mod-* et avec une structure C++ reconnue.

  1. Ouvrir Catalogue et GitHub, lire le README et les prérequis.
  2. Installer avec confirmation. Le clone temporaire est validé puis publié atomiquement.
  3. Traiter explicitement la config et les migrations documentées.
  4. Lancer Rebuild AzerothCore et contrôler les logs.
Installer ou mettre à jour ne lance jamais le code du module, son SQL, une modification de config ou le rebuild.

Mise à jour

La version distante est préparée et validée avant remplacement. La version locale complète, modifications non commitées incluses, passe dans module-backups. Elle est restaurée si la publication échoue, mais ses modifications ne sont pas fusionnées dans la nouvelle version.

Suppression assistée

  1. Cliquer Supprimer… et examiner le dossier, les configs et le SQL séparément.
  2. Tout nettoyage SQL est décoché par défaut. Les scripts officiels sont distingués des propositions déduites.
  3. Une proposition déduite est affichée intégralement, bornée, soumise à une confirmation renforcée et précédée d’un dump des tables concernées.
  4. Saisir exactement le nom du module. En cas d’échec SQL, le dossier est conservé.
  5. Après suppression, lancer un rebuild.
Ne jamais conserver une copie sous modules : AzerothCore peut la détecter comme un second module. Utiliser module-backups ou un emplacement externe.

Mettre à jour le dashboard

La liste de branches et l’indicateur d’état ne comparent que les fichiers permis par dashboard-update-manifest.json. Une confirmation en deux clics est requise ; les fichiers remplacés ou retirés sont sauvegardés.

  1. Choisir la branche, lancer la mise à jour et relire le résumé.
  2. Confirmer une seconde fois dans le délai affiché.
  3. À « Redémarrage requis », fermer la console du dashboard et relancer dashboard.bat.
Rafraîchir le navigateur ne recharge pas le backend Python. Une page plus récente que le backend peut produire des routes introuvables ou des réponses HTML inattendues.

Démarrer / arrêter le serveur

Toujours commencer dans le dossier du projet.

cd C:\azerothcore-playerbots

Démarrer tout le serveur

docker compose up -d
Le -d lance les conteneurs en arrière-plan.

Arrêter proprement les services

docker compose stop

Relancer après un arrêt

docker compose start
À éviter : docker compose down -v. Le -v supprime les volumes, donc potentiellement les bases, comptes et personnages.

Vérifier l'état

docker compose ps

État attendu :

ServiceÉtat souhaité
ac-databaseUp / healthy
ac-authserverUp
ac-worldserverUp

Ressources utilisées

docker stats --no-stream

Voir les conteneurs Docker actifs

docker ps

Logs

Suivre le worldserver en direct

docker compose logs -f ac-worldserver

Quitter l'affichage des logs avec Ctrl+C. Cela ne coupe pas le serveur.

Dernières lignes seulement

docker compose logs --tail=100 ac-worldserver

Chercher un module ou une erreur

docker compose logs --tail=300 ac-worldserver | Select-String -Pattern "MountChest|ERROR|Missing property"

Console du worldserver

Dans notre configuration, docker attach ac-worldserver a parfois renvoyé immédiatement read escape sequence. La variante avec une touche de détachement explicite est préférable. 
docker attach --detach-keys="ctrl-x" ac-worldserver

Une fois attaché, utiliser les commandes AzerothCore, par exemple :

account create test test
account set gmlevel test 3 -1

Pour quitter la console sans éteindre le serveur : Ctrl+X.

Ne jamais lancer manuellement un second worldserver depuis un shell du conteneur.

Redémarrage ciblé

Redémarrer uniquement le worldserver

docker compose restart ac-worldserver

Après modification des variables d'environnement

Un simple restart ne recrée pas le conteneur. Utiliser :

docker compose up -d --force-recreate ac-worldserver

Redémarrer world + auth

docker compose up -d --force-recreate ac-worldserver ac-authserver

Configuration Docker / modules

Notre fichier principal de personnalisation est généralement :

C:\azerothcore-playerbots\docker-compose.override.yml

Valider le YAML avant de lancer

docker compose config

Exemple actuel du bloc worldserver

    environment:

      AC_AI_PLAYERBOT_MIN_RANDOM_BOTS: "200"
      AC_AI_PLAYERBOT_MAX_RANDOM_BOTS: "500"

      AC_MOUNT_CHEST_LIFETIME_SECONDS: "120"

      - ./modules:/azerothcore/modules:ro
Si les logs disent Missing property X, vérifier le fichier de config du module ou ajouter la variable d'environnement correspondante, puis recréer le worldserver.

SQL des modules

Préférer l’updater SQL natif d’AzerothCore et le contrôle effectué par rebuild-azerothcore.ps1. Il détecte les fichiers sous data/sql, laisse le worldserver les appliquer, puis vérifie leur nom et leur SHA1 dans la table updates.

Ne pas copier une commande SQL générique depuis ce guide : la base cible, le schéma et la version du module doivent être vérifiés dans sa documentation.
Ne jamais supprimer/recréer un volume MySQL pour résoudre un problème de module. Pour une désinstallation, utiliser le plan assisté, tout décoché par défaut, et relire chaque proposition.

Sauvegarder les bases

Quand le rebuild détecte du SQL de module, il propose une sauvegarde complète de acore_auth, acore_characters, acore_world et acore_playerbots dans db-backups\<horodatage>.

  1. Accepter le démarrage temporaire de la base si elle est arrêtée et qu’un backup est nécessaire.
  2. Accepter la sauvegarde proposée avant le rebuild.
  3. Vérifier ensuite que les quatre fichiers existent et ne sont pas vides.
Le bouton Backups DB ouvre ou crée seulement le dossier : il ne produit pas de dump. Pour une sauvegarde hors rebuild, utiliser une procédure explicitement adaptée aux identifiants et conteneurs de l’installation.

Recompiler le worldserver

Dans le dashboard, cliquer Rebuild AzerothCore. Une vraie console Windows lance directement rebuild-azerothcore.ps1 afin de conserver les sauvegardes, la fusion prudente des nouvelles clés, les questions interactives et les contrôles SQL.

  1. Lire chaque question dans la console au lieu d’accepter mécaniquement.
  2. Attendre la fin du build et de la recréation du worldserver.
  3. Contrôler le résumé des configs, des SQL, l’état Compose et les logs proposés.
Une compilation manuelle avec seulement docker compose build contourne une partie de ces protections. Le bouton Patch + Rebuild applique, dans l’ordre, selfbot puis gather/grindtarget avant d’appeler ce même helper.

Installer / mettre à jour un module

Installation assistée depuis le catalogue

Dans Modules & dossiers → Installer depuis le catalogue, rechercher le module, ouvrir Catalogue pour consulter sa fiche officielle ou GitHub pour lire son README et ses prérequis, puis cliquer sur Installer et confirmer.

Le dashboard accepte uniquement les dépôts GitHub de la catégorie officielle azerothcore-module dont le nom commence par mod-. Il clone le dépôt dans modules, accepte la structure AzerothCore actuelle (src contenant des fichiers C++) ainsi que l'ancienne structure avec un CMakeLists.txt à la racine, puis publie le dossier en une seule opération. Il n'exécute aucun script du module, n'applique aucun SQL et ne lance pas automatiquement le rebuild. En cas d'échec, le détail renvoyé par Git est affiché directement sous le module. Le dossier temporaire .dashboard-install-* est supprimé automatiquement, y compris lorsque Git a créé des fichiers en lecture seule sous Windows. Si Windows empêche malgré tout son nettoyage, le dashboard l'indique explicitement.
  1. Lire le README du module et vérifier sa compatibilité avec la version du core.
  2. Installer le module depuis le dashboard.
  3. Examiner les éventuelles étapes de configuration ou migrations SQL documentées par son auteur.
  4. Lancer Rebuild AzerothCore, puis contrôler les logs.
La présence dans le catalogue n'est pas un audit de sécurité. Ne lance pas un script ou un SQL tiers sans l'avoir examiné et sans sauvegarde adaptée. Le dashboard refuse aussi de remplacer un dossier de module existant.

Supprimer un module

Dans Modules & dossiers → État des modules, cliquer sur Supprimer…. Le dashboard présente séparément le dossier du module, ses configurations actives détectées et les éventuels scripts SQL de désinstallation. Choisir les éléments voulus, relire le récapitulatif, puis saisir exactement le nom du module pour confirmer. Les configurations actives sélectionnées, y compris les éventuels modèles .conf.dist correspondants, sont sauvegardées avant suppression. Le dossier du module est supprimé avec une gestion spécifique des fichiers Git en lecture seule sous Windows ; toute impossibilité est affichée.

Le nettoyage SQL est désactivé par défaut et modifie réellement la base. Il n'est proposé que lorsqu'un script dont le nom indique explicitement une désinstallation (uninstall, remove, delete ou drop) se trouve sous sql/ ou data/sql/, dans le dossier d'une base identifiable. Si le module contient seulement des scripts d'installation ou de mise à jour, l'assistant peut proposer des nettoyages strictement bornés : suppression d'une table créée par le module ou suppression de clés précises que le script réinsère. Ces propositions sont signalées comme déduites, affichées intégralement et désactivées par défaut. Les opérations non bornées et les ALTER TABLE ne sont jamais inversés automatiquement. Lire tout script de désinstallation et effectuer une sauvegarde DB avant de confirmer : le dashboard ne peut pas annuler son exécution. Si un script SQL échoue, le dossier du module est conservé. Après toute suppression de module, lancer un rebuild.
Pour exécuter une proposition déduite, sélectionner chaque bloc voulu, relire le SQL et recopier la phrase de confirmation renforcée. Le backend recalcule le plan avant l'exécution et refuse un identifiant périmé. Il exporte d'abord chaque table concernée avec mysqldump dans db-backups/module-removal. Si cette sauvegarde échoue, aucun SQL déduit n'est exécuté et le dossier du module est conservé. L'utilisateur peut aussi copier une proposition sans l'exécuter ou choisir Conserver tout le SQL.
L'onglet Modules & dossiers du dashboard vérifie automatiquement l'état de chaque module. Cette vérification est en lecture seule : elle compare un clone Git indépendant à son propre dépôt distant, ou les modules copiés au dépôt custom groupé. Aucun fichier de module, aucune configuration et aucune base de données ne sont modifiés par ce contrôle.

Mise à jour assistée

Lorsqu'une différence est détectée et que la source distante est connue, cliquer sur Mettre à jour puis confirmer. Le dashboard télécharge la nouvelle version dans un dossier temporaire, vérifie sa structure de module C++ AzerothCore, déplace la version locale complète dans module-backups, puis publie la nouvelle version. Une erreur avant le remplacement laisse le module intact ; une erreur pendant le remplacement restaure automatiquement la sauvegarde.

La sauvegarde contient aussi les modifications locales non commitées, mais celles-ci ne sont pas fusionnées dans la nouvelle version. Examiner le backup pour les reporter si nécessaire. La mise à jour n'exécute aucun SQL, ne change aucune configuration et ne lance aucun rebuild : lire les notes du module, appliquer manuellement les migrations nécessaires avec une sauvegarde adaptée, puis lancer Rebuild AzerothCore.
  1. Arrêter ac-worldserver et ac-authserver.
  2. Faire une copie du module en dehors du dossier modules.
  3. Remplacer les fichiers dans modules\nom-du-module.
  4. Appliquer son SQL si nécessaire.
  5. Recompiler le worldserver.
  6. Recréer world/auth.
  7. Contrôler les logs.

Sauvegarde correcte d'un module

Le dashboard place automatiquement l’ancienne version complète dans module-backups lors d’une mise à jour assistée.

Ne jamais laisser une copie de sauvegarde dans .\modules. AzerothCore peut la considérer comme un vrai module et générer une erreur de linker undefined reference to Add...Scripts().

Mettre à jour le dashboard

L'indicateur en haut à droite liste les branches publiées du dépôt officiel. La branche choisie est comparée à l'installation locale uniquement au moyen de son manifeste contrôlé dashboard-update-manifest.json.

  1. Choisir main ou une branche de test dans le menu déroulant.
  2. Cliquer sur Mettre à jour (ou Revenir à main).
  3. Valider la boîte de dialogue qui rappelle la branche et l'effet du retour à main.
  4. Cliquer une seconde fois sur Confirmer la mise à jour dans les huit secondes.
  5. Attendre le message de réussite, puis redémarrer le dashboard pour charger le nouveau backend.
Avant remplacement ou suppression, les fichiers actuels sont copiés dans dashboard-backups\AAAAmmjj-HHMMSS-microsecondes. Le manifeste distant et le nom de branche sont validés avant toute écriture. L'auto-update ne synchronise jamais automatiquement l'intégralité du dépôt, ni le dossier AzerothCore : seuls les fichiers déclarés sont remplacés ; les modules, configurations, volumes Docker et bases de données ne sont pas touchés.
Pour quitter une branche de test, sélectionner main (principale). Le retour remplace les fichiers gérés par leurs versions principales et supprime les fichiers qui avaient été ajoutés au manifeste de la branche de test mais n'existent plus dans celui de main. Ces fichiers supprimés restent récupérables dans la sauvegarde horodatée. Les fichiers non déclarés par les manifestes ne sont jamais supprimés.
Si le catalogue de modules affiche qu'une page HTML n'est pas du JSON, le navigateur utilise une interface plus récente que le backend Python encore en mémoire. Fermer la console du dashboard, relancer dashboard.bat, puis actualiser le catalogue. Un simple rechargement du navigateur ne redémarre pas le backend.

Mettre à jour le core

La mise à jour Git du core n’est pas une action automatisée par ce dashboard. Le fork Playerbots, ses sous-modules et les modules C++ doivent rester sur des versions compatibles.

  1. Planifier une interruption et réaliser une sauvegarde DB vérifiée.
  2. Examiner la branche, le commit, les modifications locales et les notes de migration avant toute fusion.
  3. Résoudre explicitement les conflits et mettre à jour les sous-modules requis.
  4. Utiliser ensuite Rebuild AzerothCore pour profiter des sauvegardes de config et contrôles du helper.
  5. Contrôler l’état, les migrations et les logs avant de rouvrir le serveur.
Ne pas lancer un git pull à l’aveugle juste avant une session. Le dashboard ne sauvegarde pas automatiquement le core avant une commande Git manuelle.

Problèmes fréquents

Build : rpc error ... EOF

Souvent Docker Desktop / BuildKit perd la connexion, sans erreur C++.

docker compose build ac-worldserver

Si cela recommence : redémarrer Docker Desktop, puis relancer le build.

Build bloqué vers 1840/1844

Le linker final peut être lourd. Vérifier que l'ancien worldserver ne monopolise pas les ressources.

docker stats --no-stream
docker stop ac-worldserver ac-authserver

undefined reference to Addmod_..._backupScripts()

Un dossier de sauvegarde a probablement été laissé dans .\modules.

Déplacer le dossier de copie hors de .\modules, par exemple vers module-backups, puis relancer le rebuild.

Missing property ...

Une config de module n'est probablement pas chargée. Vérifier sa config active ou ses variables dans docker-compose.override.yml, puis :

docker compose config
docker compose up -d --force-recreate ac-worldserver

read escape sequence avec docker attach

docker attach --detach-keys="ctrl-x" ac-worldserver

Puis quitter avec Ctrl+X.

Port MySQL déjà utilisé

Contrôler le port effectivement déclaré par les fichiers Compose rendus avec docker compose config. Ne pas modifier au hasard le port interne du service.
